# AGENTS.md — Project Car Garage

## Authority and source of truth

Before changing code, read the relevant portions of:

1. `docs/FUNCTIONAL_SPEC_V1.md` — authoritative V1 product and technical requirements.
2. `docs/IMPLEMENTATION_BACKLOG.md` — ordered build plan and definitions of done.
3. `docs/ADRS.md` — locked architecture decisions.
4. `docs/FUTURE_IDEAS.md` — intentionally deferred capabilities; **do not implement unless explicitly approved**.

If repository code and the functional spec conflict, stop and report the conflict before silently changing product behavior.

## Product guardrails

- Mobile-first product.
- V1 is a private, single-owner garage tool.
- Prefer the simplest implementation that satisfies the spec.
- Do not turn the product into generic project-management software.
- Confirmed facts rank above inferred recommendations.
- Unknown maintenance history is not overdue by default.
- Issues are observations; never silently convert symptoms into diagnoses.
- Recommendations are suggestions and must explain why they appear.
- Safety-critical technical values must come from authoritative sources; never invent torque/specification values.
- Garage data is private by default.
- VIN is onboarding metadata, not the authority for a modified vehicle's current configuration.

## Locked V1 stack

- Expo + React Native + TypeScript + Expo Router.
- Supabase backend: PostgreSQL, Auth, Storage, Row Level Security, functions/scheduled jobs where needed.
- Expo SQLite for local cache and pending offline operations.
- NHTSA vPIC for VIN-assisted onboarding only.
- PostgreSQL filtering/full-text search for V1; no dedicated vector database.
- Monorepo layout described in the spec.

Do not substitute major frameworks, databases, or architectural patterns without an ADR and explicit approval.

## AI rules

- The normal product path must require **zero LLM calls**.
- Deterministic domain logic and structured retrieval always precede AI.
- AI is optional and on-demand by default.
- AI must never own maintenance intervals, due dates, event counters, part lifecycle, task readiness, event checklist scheduling, diagnosis, or safety-critical specifications.
- AI contributes zero evidence to Knowledge Claims.
- AI provider access goes only through the internal AI Gateway/service abstraction.
- Enforce budget/model/input/output limits server-side.
- Do not silently fall back to a materially more expensive model.
- If AI is disabled or unavailable, all core workflows must continue working.

## V1 scope discipline

Do not implement items in `docs/FUTURE_IDEAS.md` unless they are explicitly promoted into V1. In particular, do not add:

- OBD/GPS/telemetry.
- Professional shop/team collaboration.
- Public social/community features.
- Broad autonomous forum crawling.
- Automated universal retailer price aggregation.
- Dedicated vector database.
- Self-hosted LLM infrastructure.
- Automatic visual diagnosis.
- Universal repair procedures generated by AI.

A `Could` requirement is a stretch feature and must not block V1 acceptance.

## Engineering rules

- Use strict TypeScript where practical.
- Keep domain rules outside React components.
- Use explicit service interfaces for meaningful business operations.
- Multi-entity completion flows (for example completing a Work Plan) must be handled transactionally/server-side.
- All user-owned exposed tables must have RLS policies and tests proving cross-user isolation.
- Never ship service-role keys or private third-party secrets in the client.
- Store timestamps in UTC; render them in the user's timezone.
- Prefer UUIDs for domain IDs.
- Keep migrations version-controlled under `supabase/migrations`.
- Add tests with each behavior, not in a final cleanup pass.
- Do not use raw row deletion where the spec requires controlled archive/delete lifecycle behavior.

## Offline rules

V1 is offline-tolerant, not fully offline-first.

Core capture should remain usable with poor connectivity. Store locally first where required and queue supported mutations for retry. Media such as photos and voice notes may exist locally while upload is pending. Do not create a complex collaborative conflict-resolution system in V1.

## Recommendation engine rules

- Implement deterministic scoring first.
- Keep weights configurable and testable.
- Show at most three related-work suggestions by default.
- Store user feedback such as accepted/rejected/deferred.
- Never auto-create a Task, Maintenance routine, or Event blocker from a recommendation without user action.
- Private debug tooling may show numeric scores; normal UI should show human-readable reasons.

## Workflow for each implementation task

1. Read the task's FR/AC references in the spec.
2. Inspect existing code before proposing changes.
3. State a concise implementation plan.
4. Make the smallest coherent change that satisfies the task.
5. Add/update automated tests.
6. Run formatting, lint, typecheck, tests, and relevant integration checks.
7. Review the diff for scope creep and security regressions.
8. Update the implementation backlog status if requested.
9. Report deviations, assumptions, or unresolved risks.

## Git and review

- Work in focused branches/commits.
- Prefer one coherent backlog task or vertical slice per PR.
- Never mix future-scope experiments into core feature PRs.
- Before merge, run Codex `/review` or equivalent focused review against the base branch.
- Do not commit `.env`, API keys, Supabase service-role credentials, certificates, or user data.

## Definition of done

A task is not done merely because the UI renders. It is done when applicable:

- Required domain behavior is implemented.
- Relevant FR and AC are satisfied.
- Tests pass.
- RLS/security is correct.
- Offline/failure behavior is considered.
- Accessibility basics are present.
- No unapproved Future Ideas were introduced.
- Documentation is updated when contracts or behavior changed.

## UI foundation

Use gluestack-ui as the V1 component foundation. Build product-specific
reusable components in `packages/ui`. Do not introduce another UI/component
framework without an ADR. Prefer shared design tokens and components over
screen-specific styling.
